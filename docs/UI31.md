# UI31 — complete affected-app locks and blue dropdowns (test release)

UI30 already set disabled DOM states on the startup/recovery switches and refused
changes in their handlers. Its switch CSS still looked enabled. UI31 uses a neutral
track, subdued control and unavailable cursor while preserving the checked state.

During an active incident, all controls in an affected app card are unavailable,
including manual actions, switches, disk/image choices, review/save, draft reload,
policy setup and saved-identity management. Collapse/expansion controls are also
held in their current state. A separate amber notice remains readable even on a
collapsed card:

> Recovery in progress. Controls are temporarily unavailable.

Status continues updating, including behind an open app confirmation. Such a
confirmation remains cancellable but cannot submit while its app is affected.
Drafts, selected storage and expansion are retained. Review tokens invalidated by
an outage are not automatically replayed. Other apps remain usable. Completion of
one incident does not release an app still affected by another incident; terminal
success or failure releases only its own temporary restriction.

The backend continues checking exact identities under existing locks. Legacy
per-drive/setup editors now also check newly requested IDs against incidents on
other drives, before any write. This closes the case where a previously unselected
app could be added to another drive during recovery. No name reassignment or
automatic policy/storage changes are introduced. Existing restoration information
is read-only guidance; this release does not add a policy-restoration operation.

Dropdown fields share the existing Docker-header dark blue. Shared touch pickers
and native fields keep their dimensions, focus/disabled states, keyboard navigation
and touch behavior. Surrounding panels and other control types retain their colors.

## Future proposal only — Reboot the computer if recovery fails

This optional feature would be **off by default** and require explicit informed
opt-in because reboot affects the whole computer and unrelated applications.
It is not implemented in UI31; there is no reboot action, timer or configuration
switch in this release.

A future design must:

- Consider reboot only after the authorized, bounded recovery attempts are exhausted
  and the incident reaches terminal failure. An email failure alone, a transient
  outage, or monitoring being off must not trigger reboot. Preserve all existing
  storage/uncertain-operation safeguards; resolve in-flight work before escalation.
- Show the affected drives, failure reason and a visible countdown before reboot,
  with an accessible cancellation action. Cancellation must persist for that
  incident, including across service restarts, without silently scheduling again.
- Persist the incident ID, originating boot ID, reason, cancellation/intent and
  escalation budget **before** requesting reboot. Allow at most one automatic reboot
  per unresolved failure episode; a subsequent failed boot must remain inhibited.
  Never reset this budget merely because the computer/service restarted, a new
  incident ID was created for the same unresolved storage, or a package was upgraded.
- Require explicit administrator re-arming or a defined, verified healthy-storage
  recovery interval before clearing the persistent inhibition. An uncertain reboot
  result must be reconciled rather than repeated. Coordinate concurrent incidents
  through one host-wide owner and one countdown.

These are requirements for a later reviewed implementation, not new recovery
behavior or a claim that reboot will repair a hardware/filesystem failure.

## Validation limits

Interaction tests use isolated synthetic APIs with the actual frontend/CSP at
320/390/768/1440 pixels. Backend tests use temporary configuration and simulated
Docker/device boundaries, including stale confirmations, overlapping incidents,
new legacy selections and repeated recovery. They do not replace a physical outage
or reboot test. A user-reported successful UI30 recovery and its received recovery
email do not resolve the separate earlier startup-email failure.
