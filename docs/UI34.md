# UI34 — explain deliberate app stops

After safe unmount, mounting storage or enabling monitoring does not restart
deliberately stopped apps. Overview and Manage Drive now explain this with a
Docker Apps navigation link when current read-only evidence supports it:

> Drive ready. Apps remain stopped after safe unmount. Start them from Docker Apps when you’re ready.

The broker requires a current-boot deliberate-stop receipt for the same drive,
no active unmount/recovery restriction, verified stopped exact container IDs,
and verified selected physical filesystems and optional images. Shared-drive and
retained boot/recovery selections are conservative display evidence only.
Unavailable Docker, missing images, stale status, cleared holds and running apps
hide the notice. Ordinary manual stops without deliberate-unmount intent do not
trigger it. Polling updates the notice independently of monitoring status.

This is read-only presentation: no starts, mounts, selection/preference changes,
receipt deletion or release. UI33 ownership, deliberate-stop safeguards and the
recovery/startup engines are unchanged.

Focused backend tests cover ready/missing/shared/image/ordinary-folder states,
identity changes, released/stale/malformed receipts and ongoing incidents.
Browser fixtures cover monitoring on/off, existing navigation, polling updates,
status failure and 320/768/1440px layouts without sending a mutation.
