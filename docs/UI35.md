# UI35 — finite drive-return waiting

Timing & recovery has a per-drive **Drive return timeout (minutes)**, default 5,
range 1–1440: “Report recovery failure if the drive has not returned within this
time.” It applies from the confirmed outage, separately from recovery delay,
USB enumeration and individual worker timeouts. Existing settings acquire the
default in memory; disk/image/container selections are unchanged. Changes apply
to future incidents, never reset a running countdown.

The incident stores its limit, remaining budget, wall deadline and boot-clock
checkpoints. Polling, service restarts and reboots never grant another full window.
Same-boot elapsed time survives a backwards wall-clock adjustment; forward jumps
can conservatively expire early. Across a reboot, an uncertain backwards wall
clock expires the budget instead of extending it. Older active incidents derive
their budget from their original confirmation. Expiry requires a fresh explicit
device-absence observation; a return observed on the boundary wins. The monitor
samples at the earlier deadline even with a longer normal polling interval.

Expiry records `return_failed` and one durable timeout outcome with the existing
notification queue in the same atomic state write. Delivery failures reuse the
same logical event and existing retry behavior. Disabled notifications still
record the timeout without queuing a retroactive alert. A running worker is not
interrupted. Verified stop/cleanup records and USB/remount budgets are preserved.

The monitor keeps detecting a later return. The same incident may use its
remaining guarded recovery budget, then verify images/apps and report its normal
success. Timeout history is retained. A later failed attempt does not duplicate
the timeout alert; neither polls nor restart replay stop/start operations.

Live drive and app status uses the backend countdown. After expiry it explains:
“Drive has not returned. Dependent apps remain stopped.” Failed stop verification
is described explicitly instead. Affected controls remain restricted; even after
a terminal subsequent failure, exact selected filesystem/image verification is
required before admission. Unrelated apps stay usable. Monitoring, deliberate
unmount holds and separate once-per-boot startup are unchanged. Historical timeout
time is separate from the live status and the original outage timestamp.

Regression checks use simulated device/Docker/email boundaries with the real
monitor, durable files, worker logic, admission and notification queue. They cover
finite expiry, boundary/late return, service/reboot/old-state continuation, clock
changes, delivery retry/disabled mail, worker races, selected storage protection,
optional images, settings revision checks and timestamped history. Browser
fixtures exercise 320/768/1440px, changing countdown/expiry, affected/unrelated app
controls, timer default/range/save/failure and live versus historical presentation.
Physical no-return/reconnect acceptance is a separate test; fixture success does
not establish hardware recovery or SMTP receipt.
