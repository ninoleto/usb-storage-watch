# UI30 — recovery controls and boot-notification diagnostics (test release)

While a storage incident is active, affected apps show:

> Recovery in progress. Controls are temporarily unavailable.

Manual Start/Stop/Restart, startup/recovery selections, Docker policy setup and
saved-entry changes are refused for those identities. Drafts and selections remain
visible. Read-only status and unrelated apps remain available. Multiple incidents
are combined: completing one cannot unlock an app still affected by another.
Terminal success or failure releases the temporary restriction; this does not
remove existing identity, storage, cleanup or operation safeguards.

Backend acceptance rechecks incident state under the existing per-container lock;
legacy settings routes are guarded too. Busy/rejected actions are not queued or
replayed. New incidents retain their selected full container IDs. Older incident
state uses explicit saved identities and observed receipts, never name reassignment.
Unusable state fails closed for selected identities. Automatic workers retain their
existing stop/verify/unmount/recover/mount/start/verify/notify sequence and locks.

HDD standby & noise control is a darker, always-expanded subsection of Timing &
recovery limits. Timing and standby keep separate validation, drafts and save actions.

Future boot-email attempts retain an attempt ID/time, exit status when available,
and an allowlisted failure reason (for example DNS, verified TLS, SMTP authentication
category/code, or delivery timeout). Arbitrary stdout/stderr, SMTP responses,
addresses, credentials and exception messages are not stored. Advanced app details
show the notification outcome and retained reason. SMTP acceptance is not proof of
inbox delivery. An earlier failed receipt without diagnostics remains unexplained;
upgrading does not invent a reason, resend email or change retry behavior.

## Validation and limits

Isolated tests cover incident stages, overlapping incidents, terminal release,
repeated recovery, exact identities, stale browser reviews, legacy settings routes,
no queued commands, existing operation locks, notification sanitization and no
repeat startup/email. Browser fixtures use production assets/CSP at 320, 390, 768
and 1440 pixels; they cover preserved drafts/expansion, unrelated app control and
independent HDD/timing saves. These simulations do not establish physical recovery,
a new real reboot, email delivery or application file integrity.

Install only on an authorized test host. Preserve private configuration/state and
the preceding package before installation. Package rollback preserves current
configuration and historical receipts; review later edits before restoring any
private configuration backup. No deployment or publication is implied.
