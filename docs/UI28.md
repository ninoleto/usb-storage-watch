# UI28 app startup and recovery settings

Version `2.0.0~ui28`, local test release. Docker & Applications keeps actual
container names, runtime indicators, collapsible blue headers and independent
manual Start app / Stop app / Restart app controls.

Computer startup and Drive recovery have separate switches and drive/image
selectors. Panels appear side by side on wide screens and stack on smaller ones.
Turning a switch off disables its controls and retains choices for later reuse.
Ordinary external folders need no virtual image. Selected images stay visible;
only configured names and mountpoints are displayed. No inferred mappings are
added. Monitoring and automatic-mount warnings appear beside affected drives.

Review changes is available only for changed settings. The review describes the
result and any required Docker policy or selected-service Compose edit. Save
settings explicitly confirms it. Existing session/CSRF, pinned-ID, policy backup,
Compose override validation and readback protections remain. Unsupported external
managers receive source instructions; the UI does not claim their source changed.
No compose up, app restart, mount or monitor operation is part of saving settings.
An enabled boot coordinator may subsequently start an app when its storage is
ready, subject to its existing once-per-boot receipt and manual-stop rules.

Advanced details contains policy/manager, reported Compose source, full container
identity, original-policy restoration guidance and startup status. This is not an
application-crash watchdog. Boot startup respects later manual stops; selected
drive recovery can independently start an app after an outage.

## Persistence and failure handling

The existing engine configuration remains authoritative. A private configuration
file, `application-choices.json`, remembers disabled recovery choices and existing
per-app options such as stop grace. It does not authorize recovery or assign a
replacement ID by name. Boot choices use the existing boot configuration. Missing
disabled prerequisites can remain visible for repair before enabling them again.

Each save uses the existing guarded policy, recovery-config transaction and boot
settings operations, with revision checks. It is not one atomic transaction across
Docker, Compose and all configuration files: verified earlier stages can remain
applied after a later failure. The UI reports those stages, reads current settings
and retains the remaining draft. A lost response is read back, never replayed;
policy/source confirmation remains unverified if its response is unavailable.

A legacy drive-level disabled Docker setting containing other saved apps cannot
be silently enabled or cleared by this editor. Such a conflicting enable is
refused for explicit review of the existing drive configuration. Other apps,
monitor settings and global image-recovery flags remain unchanged.

## Validation and rollback

Focused backend fixtures cover independent settings, retained choices/options,
optional images, exact identities, stale revisions, authentication, policy failures,
partial saves and external manager refusals. Browser fixtures cover 320, 390, 768
and 1440 pixel widths, touch controls, warnings, manual actions and failed/lost save
responses under production CSP. Policy/Compose, boot/manual and repeated recovery
regressions use isolated filesystem and simulated Docker/device boundaries.

The release procedure backs up private configuration/state and the previous
package before installation, checks packaging/privacy and verifies installed UI
bytes and unchanged live selections/runtime. No new physical USB or reboot test
is required for this interface release; earlier UI25 evidence remains separate.
Rollback installs the retained UI27 package. It preserves current engine settings;
UI27 does not expose UI28's retained disabled recovery choices. Restore private
configuration only after reviewing any settings changed since the backup.
