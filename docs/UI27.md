# UI27 network address selection

Version `2.0.0~ui27`. Advanced → Network access offers **Automatic** and **Manual
selection**, independently of the LAN-access toggle. Existing configurations stay
Manual until an authenticated change is tested and confirmed. Localhost remains
independent; disabling LAN access stops the network listener.

Automatic mode uses local Linux iproute2 JSON address/route information and sysfs
physical-device identity, without NetworkManager-specific dependencies. Only up,
usable physical interfaces with assigned private IPv4 addresses qualify. Docker
bridges, VLANs and other virtual/VPN interfaces are excluded from automatic
selection and remain explicitly selectable in Manual mode. Deprecated, tentative,
expired, loopback and public addresses are ineligible. IPv6-only access is not
supported by this release.

Selection is deterministic: eligible default-route connections first, then lowest
route metric, interface name and numeric address. Without a default route, the
same stable interface/address ordering applies. The selected interface is shown.
The app binds one address only; it never changes DHCP, connects an interface or
enables a VPN.

A separate broker thread checks approximately every three seconds, including
after reboot. Address changes use the existing durable network transaction and
rollback machinery, serialized with manual connection tests. Only the LAN
listener changes; localhost is restarted only for an explicitly changed localhost
port. Normal repeated checks do not restart a healthy listener. No eligible
address means **Waiting for a network address**, with no failed-start loop.
Actual listener failures have a bounded retry delay (60 seconds); a changed
address/configuration can be reconsidered immediately.

Manual mode retains the selected address across disconnects. Its unavailable URL
is not advertised or copyable; the UI offers switching to Automatic. URL cards
are populated only after the listener responds successfully on a currently
assigned local address. HTTPS checks verify the certificate chain, address and
exact presented certificate. Losing an address or verification hides the URL.

HTTPS stays HTTPS during automatic changes. A server leaf can be renewed under
the existing trusted CA when its matching signing material is retained. A valid
existing certificate covering the new address can also be reused. If neither is
possible, automatic switching stops with a certificate explanation; it never
silently substitutes a CA or disables verification. An explicit settings change
can prepare a replacement CA, require acknowledgement of the trust replacement,
and test/confirm the proposed HTTPS endpoint. Clients may then need to import that
new CA. Private keys are never downloaded. No operating-system trust store is
automatically changed.

Enabling Automatic while offline can be confirmed through localhost. The listener
waits for an eligible address, with the chosen HTTPS policy retained. Manual
changes still use the exact proposed-origin confirmation, expiry, cancellation
and interrupted-commit rollback protections. Discovery/probes never contact
arbitrary remote addresses; readiness checks require a currently local address.

Unit tests simulate DHCP/address loss, selection, reboot and service failures;
temporary certificates use real OpenSSL. Browser tests use synthetic APIs. An
installed-host self-connection validates the selected hotspot listener separately.
No DHCP changes, physical disconnect, host reboot, remote-client trust import or
unrelated USB/storage recovery test is implied by these checks.
